# WaveLab

WaveLab is a local HTTP service for tow-tank experiments. The original equipment and interlock pages expose a fixed commissioning diagnostic scenario. Operator measurements are a separate live data path.

Set `WAVELAB_DATA_DIR` to choose the archive directory (default `data/wavelab`). `POST /api/measured-runs` accepts `name`, `model_name`, `section`, and `carriage`. `POST /api/measured-runs/{id}/evidence` accepts `kind` (`wave_time` or `force`), `source_id`, finite `value`, `recorded_at` in RFC3339 form, and an optional `batch` naming the sampling batch. `GET /api/measured-runs`, `GET /api/measured-runs/{id}`, and `GET /api/measured-runs/{id}/analysis` return the supplied records and wave/force summary. Measurements are committed to `operator-measurements.json` before they are published in memory, and are reloaded when the service restarts. The archive does not automatically grant a safety permit or drive hardware.

To see waves propagate along the flume, `PUT /api/measured-runs/{id}/probes` records the probe installation coordinates (`probes`: `source_id` + `position` in meters from the wave maker, plus optional `flume_length`), and `POST /api/measured-runs/{id}/batches` marks a sampling batch's time base as `confirmed` or `unknown`. The analysis then adds a `propagation` section: confirmed batches are mapped to flume positions as same-time-window `windows`, crest-arrival `delays` between adjacent probes, and `uncovered` regions without probes. Batches whose time base cannot be confirmed stay in `unknown_batches` and are never mapped.

The `internal/probe`, `internal/force`, `internal/permit`, `internal/carriage`, `internal/track`, `internal/wave`, `internal/absorber`, and `internal/journal` packages provide component logic for further work. Their diagnostic use does not imply that the original HTTP pages accept real sensor streams.
